# Writing Principles for This Repository

I want my GitHub documentation to sound like me, not like a corporate report or a sales pitch. It should be understandable to someone looking at my work for the first time.

## My approach

- **Use my voice.** Write plainly and naturally, preferably in the first person when describing my own work. Don't invent personal experience, decisions, tests, or results. If the wording is AI-drafted, it still needs my review.
- **Practice Shibumi.** Keep what helps the reader understand the project. Remove filler, repeated explanations, needless headings, and jargon that doesn't add anything. Simple doesn't mean vague.
- **Put the important things first.** Start with the problem, what I'm doing about it, and the actual state of the work. Put detailed technical explanations where they're useful rather than repeating them everywhere.
- **Keep the details that matter.** Requirements, safety boundaries, reproducible setup instructions, test evidence, and limitations should not be lost just to make a document shorter.
- **Be clear about AI.** Label work accurately as AI-led or human-led, and explain AI's actual role without making a bigger production out of it than necessary. Human-sounding prose is not proof that I wrote it without AI. Also distinguish AI used *to develop* something from AI that actually runs *inside* the finished product.
- **Don't claim work I haven't done.** A plan is a plan. Draft code is not a tested application. Keep status and results current, with evidence when something is complete.

When editing, I'd rather revise the original explanation than append another section saying the same thing.

These principles guide future GitHub writing and revisions. They apply alongside each project's own technical and disclosure requirements.

**AI transparency:** I set these writing preferences and asked for them to be applied consistently. AI drafted this guide for my review.
